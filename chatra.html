Chatra

The problem

Teachers were managing classrooms through Telegram chats and spreadsheets.

At my university, educators had no unified tool. Assignments were sent as messages, attendance was tracked in notebooks, and grades lived in disconnected Excel files. Students had no visibility into their own progress.

The goal was clear: build a platform where teachers create classes, post assignments, track attendance, and publish grades — and where students access all of it from a single app.

Mobile app

Flutter, built to feel native on iOS and Android.

Architecture

Three independent layers. One coherent product.

Every layer was designed to be independently deployable but tightly integrated via a shared REST API.

Flutter Mobile
Riverpod state management · GoRouter navigation · Dio HTTP client · SharedPreferences for token persistence · ngrok tunneling for iOS simulator
FastAPI Backend
JWT authentication · PostgreSQL with SQLAlchemy ORM · Docker containerisation · Auto-generated Swagger docs · Role-based access control
Nuxt.js Dashboard
Kazakh & Russian i18n · Role-based UI (teacher / student / admin) · Real-time grade updates via REST polling

Things learned the hard way

What I learned

The hard parts were the valuable parts.

iOS simulator networking with a local FastAPI server required a tunneling setup with ngrok — something no tutorial covered. I figured it out from first principles.

Designing a role-based system (student, teacher, admin) across three platforms meant every API endpoint and every UI screen had to account for permission states. It forced me to think about product architecture, not just code.

Shipping to real users — even a small group — changes how you build. You stop writing code for yourself and start writing it for people who will break your assumptions in ways you never anticipated.
